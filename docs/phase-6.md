`tools/planning/schemas.ts` is the schema source. `npm run schemas:record` intentionally publishes it; `npm run schemas:check` compares every generated file and independently compiles it with strict AJV 2020. Presentation schemas use numerical metre values, including fractions; they are validated by AJV rather than expanding the deliberately limited headless semantic-schema interpreter.

`validatePlanning()` rejects malformed shapes and unknown fields, then checks local references and uniqueness: anchor/node names, exit directions, source-object placements, asset materials/hotspots and label bindings. Spawn, exits, objects and features must refer to declared anchors. Label placeholders must match the declared slots exactly; YES/NO and FINISH choices must match their decision context. Scenery cannot claim source objects or interactive hotspots. This does not yet check every source reference, render a scene, implement flag evaluation or validate GLB contents.

All files carry explicit provenance and review state. Manual examples name an author; generated drafts must name a model, prompt version and input hash. An approved record also requires a reviewer and review date. Schema validity does not grant approval. All pilot examples remain **drafts**, pending individual art review against the approved style bible.

### Coordinates and authority

Positions are local to each room: metres, right-handed coordinates, +Y up, +X east and -Z north. Size vectors are width/height/depth in metres; yaw is degrees. Compatible connected rooms may eventually share a GLB with separate named room roots and transforms; incompatible connections retain separate scenes and transitions. These coordinates do not impose a globally consistent map. The 6.1 schemas still describe individual room plans; a group manifest and its consistency checks remain later work. Dimensions and materials in the examples are proposed art choices rather than facts extracted from ZIL. `outdoor` is supported by the format but must only be selected when the room context justifies it.

Exit `availability: engine-option` and object `visibility: engine-observation` retain the engine as authority. A null exit destination represents a blocked or computed destination; it must not become an invented connection. A non-null destination alone does not make an exit traversable. Kit parts are decorative geometry. Separate feature nodes can declare flag/global equality conditions without executable expressions or arbitrary code. The approved, source-checked mapping into safe renderer observations belongs to 6.5 and later presentation work; the schema alone does not authorize reading hidden state or revealing a concealed feature.

Hotspot definitions name volumes only; they do not execute routines. A sphere's size vector describes its enclosing bounds; concrete geometry validation belongs to the asset validator. Labels bind to stable source syntax families (for example `TAKE:8`), with selected object/word text substituted later. They never submit an action without the current engine option and its correlation checks. Existing phase 4 labels remain in use until the reviewed label integration in 6.6.

## Source context builder (6.3)

`tools/planning/context.ts` analyses a fresh pinned source compilation without creating a session, executing a handler, sampling RNG or calling a model. `npm run contexts:record` deliberately writes the generated artifacts in `games/zork2/planning/context/`; `npm run contexts:check` regenerates them in memory and rejects missing, edited or obsolete files without overwriting them. CI runs the check. The generated README links to all **86 room files**; shared catalogues describe **165 objects** and **414 runtime routines**. Replaced/parser-only routines are outside the presentation catalogue.

Each room file retains its source name and DESC, LDESC property (including a blank or missing static description), source flags and spans, declared lighting, original exit kind/declaration, and known neighbouring room names. Blocked exits have no invented destination. Computed exits retain their routine rather than guessing its return value. CEXIT global conditions and DEXIT door identities stay explicit. RLANDBIT means land and cannot establish whether a room is outdoors; the context requires source-text/art review to choose a shell.

Initial object membership follows the complete declared parent chain, including objects nested inside containers. The object catalogue preserves descriptions, initial parents, flags and handlers, and distinguishes INVISIBLE from merely unlisted NDESCBIT objects. It also marks invisible ancestors and initially closed opaque containers. Room-local GLOBAL references, universal global-object references and explicit script arrivals are separate from initial contents; global/pseudo objects are not automatically modelled as physical props.

All rooms reference a conservative catalogue of **128 potential arrivals**. It includes source TAKEBIT/TRYTAKEBIT objects, actors/vehicles, literal script-moved objects and contents of potentially portable containers. This is an over-approximation for asset planning, not a proof that every listed object can actually reach every room. It must never be interpreted as a room's initial population, currently visible objects or legal options. Runtime source checks and the later consistency/review pass retain authority.

Room, local-object, pseudo and computed-exit handlers seed a static helper-call traversal. The catalogue preserves every output fragment from those routines, unresolved dynamic output operands, complete original routine source and source spans. Literal fragments are not concatenated into one unconditional room description: their original guards remain visible in the routine source. Global declarations (including text tables) are retained for reviewing symbolic output and state dependencies; compiler-only declarations can explicitly lack source text. Dynamic APPLY targets remain unresolved. Lifecycle/dispatch routines such as PERFORM, GOTO, DESCRIBE-ROOM and CLOCKER are recorded as boundaries rather than recursively attaching unrelated gameplay text to the room.

A whole-program mutation index records literal FSET/FCLEAR/MOVE/REMOVE/PUTP targets and global assignments/updates, with source excerpts and references. Feature records point to this evidence, while room state dependencies point to the globals' writers. This catches changes outside a room's own action routine. Generic handler targets, raw memory writes and other dynamic effects are not falsely resolved. Doors, containers, portable items and handler-backed objects remain potentially changeable even when no literal mutation names them. Every feature requires state review; lack of recorded literal evidence is not a certification that geometry is static. Removal is evidence of disappearance, not proof of destruction.

The index records builder version, semantic build identity and shared-catalogue hashes. Each room has a canonical hash of its own context; catalogues are hashed separately. The future 6.4 planner must include the actual referenced catalogue slices, style content and approved image in its prompt/cache identity rather than relying on a room hash alone. Output keys are canonicalised, source arrays retain order and all returned records are owned copies. No timestamps, network services or environment paths enter generated context identity. The derived Zork source text retains its MIT notice beside the generated files.

These files are offline authoring data containing spoilers. They are not imported by the browser presenter or placed in player observations. They provide source evidence for later reviewed scene plans; they do not approve those plans, infer executable reveal predicates or implement a group-GLB renderer. The next step is 6.4, the validated planner client and committed-output/cache workflow.
