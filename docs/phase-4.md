## Candidate families and static ranking (4.1)

`buildCandidateCatalog(game)` reads the frozen bundle's vocabulary, world metadata and translated IR. `generateCandidates(game, catalog, scope)` accepts an explicit actor, room, operands and current immediate parents. Neither function imports or runs the interpreter, calls source scope helpers, executes a handler, changes the world, or consumes random numbers. The scope argument is an input contract, **not proof that its objects are visible or reachable**. The completed step 4.2 query constructs this input from the current world.

Each family preserves the lexical table, one-based syntax row, source action and zero, one or two slots. Slot lists are independent: with N scoped operands, a two-object family stores 2N entries rather than N² pairs. Zero-object families remain present with an empty scope. Every dictionary exit direction is offered, including directions with no usable exit; execution retains the original refusal and turn cost. No rank, handler result, possession rule or attribute removes a candidate.

Syntax semantics stay separate:

- `FIND` is retained as an omitted-object inference hint. It does not filter a slot: `ATTACK AQUARIUM WITH SWORD` remains representable despite `FIND ACTORBIT`.
- `HAVE` and `TAKE` are recorded as possession rules for the existing commit-time adapter checks. Unheld tools remain candidates.
- `MANY` records the source's multiplicity permission; this step does not build multi-selection actions or bypass `MANY-CHECK`.
- `HELD`, `CARRIED`, `ON-GROUND` and `IN-ROOM` can add a small ranking bonus when the caller supplies the matching scope sets. They never restrict membership.
- `SAY`, `ANSWER` and `INCANT` families are marked as quoted-word input. The vocabulary picker and actor continuation UI belong to 4.4.

The two source-shadowed rows, `CLIMB:6` and `CLIMB:8`, remain in the audit with an explicit `shadowedBy` reference. The original parser and existing planner choose the first matching operand-count/preposition pattern. These audit rows are not newly executable choices. Staged option construction must respect that marker rather than submit a row the planner rejects.

## Ranking evidence

The analyzer collects action-symbol references in each routine and follows named calls and literal routine-valued APPLY targets to a fixed point, including recursive helpers. Each boost records the owning entity, dispatch layer, root handler, actual mentioning routines and whether the root was assigned dynamically. `PERFORM` is a dispatch boundary: following its generic dispatch machinery would incorrectly smear every action across every handler. Conditions are never evaluated; evidence means that a handler mentions an action, not that the action will succeed or that the puzzle is currently solved.

All dispatch layers are represented: actor ACTION, room ACTION (including M-BEG branches), syntax preaction, indirect-object ACTION, direct object's current parent's CONTFCN, direct-object ACTION, default verb and room pseudo handlers. M-BEG uses the actor's immediate parent from the parent map, falling back to the supplied room; this correctly includes BUCKET-FCN when riding inside the bucket. The catalog also scans all runtime `PUTP ACTION/CONTFCN` writes. It retains both initial and replacement handlers, including `MAGIC-ACTOR` on the adventurer. A clearing write does not erase static evidence. An unresolved write is recorded explicitly; literal routine references in its writer provide conservative fallback evidence. The current Zork II corpus has one unresolved ACTION write, the PSEUDO-OBJECT pointer read in GLOBAL-CHECK; all possible declared pseudo handlers are separately analyzed and keyed by room/word. Unresolved APPLY sites are also listed rather than claimed to be fully resolved.

Initial weights are transparent: a mention through an actor, room, operand, container or pseudo handler adds 100; a syntax-bound preaction adds 10 and its default handler adds 1; a matching scope hint adds 1. Each operand receives its own score. A family score is shared evidence plus the best score in each independent slot; it does not assert that those selections are jointly valid. Equal scores use code-unit identity ordering, independent of host locale. These weights are an initial heuristic; knowledge gates and the final first-page policy remain 4.5–4.6.

The collar-on-Cerberus family receives indirect-handler evidence from CERBERUS-FCN, ANSWER/SAY receive room evidence in the riddle room, and taking an item currently inside the bucket receives BUCKET-CONT evidence. Moving that item elsewhere removes only the bucket's ranking contribution. Pseudo features keep explicit room/word identity. Results own their mutable arrays and operand objects, so changing a returned list cannot affect another query, its input, or the catalog.

## Staged object and actor selection (4.3)

`GameSession.actors()` offers the player and currently visible ACTORBIT entities. `select({ expected, actor, family, operands })` reviews a caller-owned partial draft at the current epoch/revision. The family key is the catalog's lexical-table/row key (for example `PUT:7`); directional movement uses `walk:EAST`. A view returns the selected operands, whether the selection is ready, and the next slot's ranked object choices, source spellings and multiplicity permission. It contains no executable option ID or action plan. An empty operands array begins selection, one operand advances a two-object action to its second slot, and slicing/clearing that array implements back/cancel without engine state. Staging does not reserve objects or advance protocol counters.

Every stage uses fresh actor-relative scope. Both first and second operands can come from the robot's own inventory, and unheld objects remain offered regardless of HAVE/TAKE/FIND. No Cartesian product is constructed. Lexical variants retain source noun/adjective bindings, including adjective-only inputs such as CANDIED. Choosing a bare object identity uses the first supported adjective/noun spelling when available, falling back to its source noun. Every supported source noun, noun/adjective combination and lone adjective is available in the choice's `spellings` list. These spellings are not a speculative test of whether a handler will succeed; unresolved source ambiguity still fails atomically in the adapter. The underlying operand validation was extracted from `prepareAction` into the shared pure `prepareOperand`; action planning semantics are unchanged.

`commitSelection(request)` rechecks identity, ordinary input state, actor availability, family, source shadowing, each selected object's scope and its declared spelling. It requires all slots, permits explicit multi-selection/ALL only for MANY slots, rejects duplicate identities and preserves the existing simultaneous-multiplicity/shared-pseudo exclusions. Only then does it call `prepareAction`, mint the canonical option ID, and execute the action on an isolated turn-loop fork. Existing source MANY-CHECK, TAKE-CHECK, PERFORM, actor handlers and CLOCKER determine the result. Implicit acquisition happens as part of the same command; a possession refusal remains an ordinary original-game refusal. A failed plan or execution cannot install partial inventory changes, output, RNG consumption, protocol counters or an accepted log entry.

A successful result carries `optionId`. Accepted-input logs add a `selection` entry with the reviewed request and canonical ID; `GameSession.replay()` reconstructs the committed selection without replaying browsing or depending on transient issued options. Altered IDs fail the normal accepted-log equality check. `execute()` continues to accept only the existing trusted integration/decision IDs; it does not start decoding arbitrary JSON IDs or authorize an old staged commit merely because its ID is known. Restore, restart and every committed action invalidate stale drafts through epoch/revision checks. Saves contain no partial draft or UI selection state, and save/bundle formats remain unchanged.

For example, with the teapot in scope:

```ts
const { epoch, revision } = session.observe();
const draft = {
  expected: { epoch, revision }, actor: 'PLAYER', family: 'PUT:7',
  operands: [],
};
const first = session.select(draft);
const second = session.select({ ...draft, operands: ['KEY'] });
const ready = { ...draft, operands: ['KEY', 'TEAPOT'] };
session.select(ready); // ready, still no game time or option ID
const result = session.commitSelection(ready); // mint ID and execute one command
```

Every resulting text boundary matches the original binary and consumes the exact original random tape. Other walkthrough commands still use the established integration catalogue in this test; complete all-option play and broader ordering coverage remain 4.9. Separate original-story tests cover implicit taking, an unheld possession refusal and a two-object robot command that puts its own iron key into its own teapot, followed by normal player input. ## Saved knowledge gates (4.5)

`games/zork2/gates.json` defines six initial, hand-written policies: the riddle answer, robot instructions, balloon landing word, collar/Cerberus pairing, repellent instructions and FLOAT incantation. Each rule records its source provenance, literal printed clue fragments and structured action predicates. These are a limited initial set, not complete coverage of every puzzle. Predicates match actor, verb, direct/indirect object identity or selected words; alternatives within a field are OR, fields are AND. Compound object gates apply to the next choice after the earlier operand is selected, rather than demoting every PUT action. Repellent targets cover both SPRAY operand orders, including the source SSPRAY forwarding verb.

`knowledge.ts` evaluates this metadata without executing game code. Unlearned matches receive `placement: 'more'`, gate IDs and a fixed rank penalty. Primary choices sort first with deterministic identity tie breaks. Every original family, actor, operand and trusted integration option remains present; fully selected gated actions remain executable. The word picker stays context-independent and alphabetic, including WELL and FLOAT before their clues. Only a completed phrase receives gate placement. Final first-page sizing and the reachable “more” presenter belong to 4.6 and the player shells; this step establishes their explicit placement contract.

Knowledge is earned only from literal clue text emitted by a successfully committed engine boundary. Queries, hidden source text, failed transactions and speculative handler execution cannot teach a clue. Learning occurs before constructing a primitive SAVE payload. Saved IDs are unique, sorted and checked against the bundle's rules. Boundary import and primitive RESTORE recover the saved snapshot; death and resurrection retain current knowledge, and restart clears it before processing fresh opening output. Replay reconstructs the same knowledge from committed output. User-editable saves validate identities and canonical structure, not cryptographic proof that a clue was previously seen.

Gate metadata participates in the semantic bundle hash and uses policy ABI **zxr-gates-v2**. Recompile bundles for this policy; older saves have a different build identity and are rejected. Action/option encoding and translated ZIL game rules are unchanged. Future gate edits require replay and reachability validation; the broader phase 4.9 and phase 5 checks remain ahead. ## Ranked menus and one-step expansion (4.6)

`GameSession.menu(actor, { firstPageSize })` projects fresh, actor-relative candidates into object groups, an action-first path, exits and a separate always-available menu for LOOK, INVENTORY, WAIT, SCORE and SAVE. The default first-page limit is eight; six and seven are also supported. Each section returns `{ primary, more, total, hasMore }`. “More” contains the entire remainder, so expansion takes one step rather than a series of hidden pages. Gated entries always stay in `more`, even if fewer than eight ungated choices exist. Exits retain blocked directions and the actor's knowledge placement.

Object groups bind only the first operand and use that object's static evidence in place of the best first-operand score. They do not inherit another object's higher score. Other slots remain independent until selected. Choices sort by knowledge placement, descending score and code-unit family identity. The action-first path retains every supported family, including lexical alternatives, zero-object special inputs and the unbound first slot needed for MANY/ALL. The two source-shadowed CLIMB rows remain in the candidate audit, rather than appearing as drafts that the existing planner would reject. Object groups and independent stage lists never materialize every possible two-object pair.

A menu entry contains a browsing key and a `SelectionRequest` draft carrying its epoch/revision. It contains no executable option ID. Passing that draft through `select()`/`commitSelection()` preserves source spellings, ordinary refusals, implicit taking and atomic validation. `selectionMenu(draft, policy)` applies the same first-page/more projection to the next operand's complete list, including compound knowledge gates, lexical spellings and the existing ALL permission. Word selection keeps its separate neutral vocabulary picker. Menu queries, expanding/collapsing and cancelling drafts neither learn clues nor consume turns or RNG. Decisions remain in `options()`; ordinary menus are empty during decisions, host operations and terminal state.

```ts
const menu = session.menu();
```
